# 日時変更の組織・所属認可 (#169)

日時変更の提案・承認・辞退・撤回は、認証ミドルウェアが設定した本人IDと
アクティブ組織を必須とする。画面は現在の組織を送るが、本番では認証
ミドルウェアがそのヘッダーを上書きするため、クライアントの指定を信用しない。

HTTPは ScopedRescheduleStore.RescheduleInOrganization のみを使用する。
旧 Reschedule だけを実装した保存先へのフォールバックはなく、503を返す。
旧メソッドは既存の内部呼出し・低水準の競合テストとの互換性のために残るが、
HTTPの認可済みエントリーポイントではない。

Firestoreは同一トランザクションで依頼の組織、両当事者の所属文書、
アカウント削除フェンスを確認する。Postgresは依頼行をロックし、
両当事者の所属行を FOR SHARE でロックする。これらは状態遷移と
同一操作の再送判定より先に行う。

- 本人・組織が欠けるHTTPリクエスト: 401
- 他組織、第三者、存在しない依頼: 404
- 依頼の当事者のいずれかが所属を失った場合: 403 / membership_required
- 同一再送: 現在の認可を満たす場合のみ従来どおり200

認可失敗では元の確定枠、変更候補、通知、監査ログを変更しない。
承認時の空き状況・二重予約検査と、通知・監査の一括保存は既存処理を使う。
所属削除が後から完了する場合、変更が先に認可・確定したという順序は許容する。
すでに確定した操作を所属変更で遡って取り消すものではない。

HTTPテストとFirestore/Postgres統合テストで全4操作の拒否・正規操作・再送を
検証する。テストは架空のユーザーと隔離DBを使い、本番の予約や所属を変更しない。
Google OAuth審査、実Googleアカウント同期、他の予約操作の認可監査は別の範囲。

# 別時間の提案と依頼者の合意

Issue #141 / Epic #102。担当者が別時間を提案し、依頼者が承認して会議を確定する。

## 動作と権限

- 未確定の依頼の現在の担当だけが、未来かつ依頼期限内、依頼の所要時間と同じ長さの会議候補を提案できる。
- 提案者は入力から受け取らず、サーバーが proposedByUserId に現在の担当を記録する。
- 自動生成候補・提案者未記録の旧候補は担当が承認する。明示提案した候補は依頼者だけが承認する。提案者による自己承認、依頼者による自動生成候補の自己承認は禁止する。
- 担当引継ぎでは従来どおり候補を差し替え、提案者情報も消去する。前担当の提案を、新担当の同意として再利用しない。
- 提案だけでは予約しない。空き状況が変わる場合があるため、承認トランザクション内で最新の公開投影・同期鮮度・双方の確定済み調整との重複を検証する。
- 外部カレンダーへの自動登録はしない。合意後は既存の双方の確定表示・ICS出力を利用する。

## 再送・競合・通知

提案IDは依頼ID、担当ID、UTC・マイクロ秒精度に正規化した開始/終了日時から生成する。同じ時間の再送は同じ不変の候補を返す。全候補は1依頼10件まで。既存候補は無断で差し替えず、相手がいずれかに合意できるよう保持する。

同じ提案の再送は期限超過・回答終了後も、現在の担当と所属が一致すれば受付確認だけを返す。新しい候補の追加は不可。再送で状態や通知の既読を変更しない。提案の受付確認は現在の依頼状態の再取得ではないため、別端末で操作した場合は一覧を更新する。

Firestore / PostgreSQLで、候補・更新時刻・依頼者への通知・操作主体が担当である監査を一括保存する。承認も予約・担当への通知・操作主体が依頼者である監査を一括保存する。通知/監査の衝突時は全体を巻き戻す。どちらの通知にもタイトル・予定詳細は複製しない。

初回と再送の両方で依頼者・担当の所属を検証する。Firestoreは既存の全参加者削除フェンスも検証する。承認・文章回答・引継ぎの競合は依頼単位のトランザクションで直列化する。提案が先に保存され、その後回答・引継ぎで終了する順序は正常である。

UIは不明な送信結果の日時を固定し、同じ日時で再試行する。承認結果が不明な場合は同じ候補だけを再試行できる。二重操作を同期的に抑止し、画面離脱時は通信を中断する。離脱でサーバー処理の取消が保証されるわけではない。

## 移行とロールバック

PostgreSQLは起動時に coordination_request_options.proposed_by_user_id の nullable 列を追加する。Firestoreは追加フィールドのみ。既存候補の提案者は推測せず、従来の担当承認を維持する。

運用開始後は、提案者に応じた承認権限を保持した修正版へ切り戻す。旧バイナリはこの権限を理解せず、提案者自身による承認を許してしまうため、そのまま旧版へ戻さない。追加列を削除しない。

提案者は常に現在の担当であり、担当引継ぎで旧候補を消去する。従来の関係者削除で候補も依頼と一緒に削除する。新しい保存期間や外部送信先は増やさない。

## 検証

純粋モデル/APIテストに加え、両DBの同時再送・確定、通知/監査衝突、所属取消、最新空き状況/予約競合、引継ぎ/回答との競合を検証する。Firestoreは削除中の操作も拒否する。ブラウザーは合成データで通信断→提案再送→依頼者承認再送→双方の確定表示とICSダウンロードを確認する。本番利用者の予定は検証用に変更しない。

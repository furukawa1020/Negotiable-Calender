# 担当引継ぎ

Issue #139。未確定・期限内の依頼を、同じ組織の別担当へ1回だけ引き継ぐ。

## 利用者から見た動作

- 受信一覧の「担当を引き継ぐ」から組織ディレクトリの管理職を選択する。自分と依頼者は選択できない。APIは同一組織の所属を検証する。
- 同じ依頼IDの担当を変更する。依頼者・本文・期限は保持する。新担当の受信一覧に表示し、依頼者と新担当へ通知する。
- 元の会議候補を破棄し、新担当の公開投影・双方の確定予約から候補を再生成する。確定時には既存の最新投影・競合検証を改めて行う。
- 新担当は会議確定・文章回答・辞退ができる。再引継ぎは不可。送信一覧には現在の担当IDを表示する。
- 元担当は引継ぎ完了後の新規閲覧・回答ができない。既に表示済みの内容を端末から回収する機能ではない。過去の通知リンクは依頼への権限を与えない。
- 通信結果が不明な場合は選択相手を固定し、同じ操作を再試行できる。

## 原子性と再送

Firestoreトランザクション／PostgreSQL行ロックにより、担当変更・候補差替え・2件の通知・監査を一括確定する。通知や監査の書込みに失敗した場合、担当だけが変わることはない。回答・確定との競合では1操作だけが成功する。

依頼者・元担当・新担当の所属をコミット時に検証する。Firestoreでは全参加者と新担当のアカウント削除フェンスも検証する。

元担当から同じ相手への再送は、新担当が回答済み・期限超過でも成功確認のみを返す。返却の status=delegated は引継ぎの受付結果であり、保存された現在の依頼ステータスではない。新担当の回答内容や現在の状態は返さず、通知の既読を上書きしない。元の依頼作成キーの再送も元の担当を基準に同一性を判定する。

PostgreSQLの一覧・詳細は権限判定、本体、候補を読み取り専用REPEATABLE READの同一スナップショットで取得する。引継ぎと並行する読み取りで旧担当の本体と新担当の候補を混在させない。

## 保存・削除・移行

- delegatedFromUserId に元担当、delegatedUserId と targetUserId に新担当を記録する。保存状態は suggested のまま新担当の回答を待つ。
- PostgreSQL起動時の既存スキーマ適用で nullable delegated_from_user_id 列を追加する。Firestoreはフィールド追加のみ。既存データの一括書換えは行わない。
- 元担当を含む関係者のアカウント削除時には、関連依頼とそれに紐づく通知・監査を削除する。履歴の個人識別子だけを残さないため、他の参加者の一覧からも当該依頼は消える。
- 元担当のエクスポートは現在の閲覧権限を基準とし、引継ぎ後の依頼・新担当の回答を含めない。
- 旧方式の status=delegated データは自動修復しない。元担当履歴のない旧データや確定済み依頼を引継ぎ対象にしない。
- ロールバックで追加列を削除しない。旧バイナリは元担当の削除・作成再送を理解しないため、引継ぎ利用開始後はこの互換処理を維持した修正版へ切り戻す。

Google OAuth審査・カレンダー書込み・多段委譲はこの変更に含まない。

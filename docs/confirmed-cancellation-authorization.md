# 確定予約取消の組織・所属認可 (#171)

取消APIは本人ID・アクティブ組織を必須とし、
ScopedConfirmedLifecycleStore.CancelConfirmedInOrganization のみを呼ぶ。
本番では認証ミドルウェアが両ヘッダーを上書きする。画面から送った組織名や
本人IDを認可の根拠として信用しない。旧 CancelConfirmed だけを実装した
保存先へのフォールバックは503で拒否する。旧メソッドは内部互換用に残る。

Firestoreは依頼・アカウント削除フェンス・操作本人の所属文書を同一
トランザクションで読む。Postgresは依頼行をロックし、操作本人の所属行を
FOR SHARE でロックする。依頼の組織一致と本人の所属は、確定候補の検査や
取消済みの再送判定より先に確認する。

- HTTPで本人・組織が欠ける場合: 401
- 依頼が他組織、第三者、または存在しない場合: 404
- 当事者本人がその組織の所属を失った場合: 403 / membership_required
- 同一取消の再送: 現在も認可される場合だけ従来どおり200

取消は新規予約を作らず、既存予約を解放する。相手の所属だけが失われた場合、
残った当事者の取消権限は維持する。双方の所属が必要な日時変更とは異なる。
アカウント自体の削除処理中は既存の削除フェンスを引き続き優先する。
所属剥奪より先に認可・確定した取消を遡って無効化するものではない。

拒否時は依頼・候補・予約枠・通知・監査を変更しない。正規取消は予約を解放し、
相手への通知と監査を一括保存する。二重送信・再送で副作用を重複させない。
Google Calendarに登録済みの予定を直接削除する機能ではなく、外部予定の
削除は既存UIの案内どおり手動で行う。

HTTPの修正前テストは、組織指定なしの成功・旧保存経路への呼出しなど
6ケースで失敗を検出した。Firestore/Postgresの統合テストは両当事者からの
操作について、本人の所属喪失・他組織・第三者・再送・相手の所属喪失後の
正規取消と、拒否時の保存内容不変を確認する。既存の並行取消、取消と再予約の
競合、通知/監査障害のロールバック、アカウント削除フェンスも認可付き経路で
検証する。すべて架空データと隔離DBを使用し、本番予約・所属は変更しない。
